# ADR 0081: Publish Apple 1.1.8 (98) and install it on the three Macs

- Date: 2026-11-02
- Status: Accepted; published and installed on three Macs; provider send acceptance pending
- Related: [ADR 0080](0080-session-list-scan-prunes-conversation-views.md),
  [ADR 0076](0076-paired-release-1-1-6.md),
  [ADR 0079](0079-install-multica-daemon-detection-fix.md),
  [DESKTOP_UPDATES](../DESKTOP_UPDATES.md)

## Context

The owner asked for two things in one request: an hourly review of the three
Macs' daemon logs for send anomalies, with fixes, and a redeployment to exactly
those three Macs plus the OTA page.

The logs show the fleet is split across three unpublished/older lines:

- M4Mini runs 1.1.6 (96), daemon build `0da52647`, the only device with real
  post-release send attempts. Ten of thirteen applied; three pre-ledger
  refusals on 2026-11-02T03:06Z are ADR 0080's session-selection defect.
- M1Max runs 1.1.5 (95), daemon build `3ae46a2f`, which predates ADR 0075
  (Claude registry navigation) and ADR 0077/0078 (Multica); its send refusals
  in the logs are older and none occur on the final version window.
- M4Pro runs 1.1.7 (97), a targeted, un-notarized local build from `071e54de`
  with no Velopack `sq.version`, so its daemon reports `0.1.0` (ADR 0079).

The published line is 1.1.6 (96). 1.1.7 (97) was never published and its
number cannot be reused for different source without obscuring provenance.

The log analysis (2026-11-02, three daemon logs through 2026-11-02T03:37Z)
found no data loss, duplicate delivery or permanent send block on the current
versions. The failure classes that remain in the historical logs are either
already fixed on `main` (draft-echo refusals, duplicate send buttons/prompt
editors, unconfirmed-latch blocking, question AX timeouts) or safe pre-ledger
refusals. The only defect with a last-seven-day occurrence on an installed
release is ADR 0080, which merged as PR 80 before this version bump.

## Decision

Publish **Apple 1.1.8 (98)** from the merge commit that carries the version
bump, and install that one verified portable on exactly M4Mini, M1Max and
M4Pro.

- **Source.** The version-bump PR starts from `main` after PR 80 (ADR 0080).
  It sets `MARKETING_VERSION: 1.1.8` and `CURRENT_PROJECT_VERSION: 98`, and
  regenerates the committed Xcode project with xcodegen 2.46.0. The release
  worktree is a clean detached checkout of the bump PR's merge commit `C`;
  `verify-release.sh` must prove the daemon's `MUSTER-BUILD-COMMIT` equals `C`.
- **macOS.** Build the release daemon, CLI, relay and browser host, the Apple
  FFI archive and the Developer ID macOS app; package with Velopack 1.2.158;
  notarize, staple and verify strict signatures, Gatekeeper and presence
  signing. No Velopack update feed is published: no feed signing key exists on
  the publisher Mac, as recorded for 1.1.5/1.1.6 in ADR 0076.
- **iOS.** Because an Apple 1.1.8 update is published, the repository rule also
  publishes the paired iOS OTA build for the three registered devices. It is a
  development-signed archive, not a TestFlight upload or App Store export.
- **OTA pages.** Publish to the private publisher: the notarized Mac portable
  under `desktop/`, the hash-named and fixed-alias iOS OTA files under `ios/`,
  and the unified page at the root generated by `package-ota.py`, with
  `no-store` cache headers.
- **Installation.** Install the same notarized portable, not a locally built
  bundle, on only the three Macs; preserve each device identity and Secure
  Enclave key; keep a previous-bundle copy; never drive an install over the
  virtual-network address.
- **Not in this release.** GitHub Release, TestFlight upload/review, App Store
  export, physical iPhone installation, server-side pruning of superseded
  releases and a signed in-app update feed. Pruning is destructive and needs
  explicit owner authorization.
- **Hourly log review.** The owner's recurring review is configured as a
  scheduled task in the agent session (daily 08:00–24:00, hourly). This
  repository change adds no scheduler service; the review reuses the same log
  evidence and the ADR 0080 / 0075 classes above.

## Alternatives

- **Install published 1.1.6 on all three.** Excludes M4Pro (97 to 96 is a
  refused downgrade) and would not deliver ADR 0080's fix.
- **Promote the M4Pro 1.1.7 (97) build to the fleet.** It was built from
  different source, is un-notarized, lacks `sq.version` and has a `-dirty`
  stamp; it cannot pass the release gates and would hide provenance.
- **Publish a signed update feed.** Requires the offline feed key that is not
  available; publishing portable + OTA only matches 1.1.5/1.1.6.
- **Skip the paired iOS build.** The repository release-coordination rule
  requires it when a macOS update is published, and the owner asked for the
  OTA page.
- **Use GitHub Release/TestFlight.** Outside the request; those channels stay
  on their previous versions.
- **Fix the second, message-level defect (an absent Claude CLI session with no
  desktop identity produces a generic "cannot uniquely select" refusal) in this
  release.** It is a safe pre-ledger refusal, and the candidate exact-ID route
  needs device evidence; it stays a documented follow-up instead of shipping a
  blind navigation change.

## Consequences

- All three Macs end on the same notarized 1.1.8 build whose daemon stamp
  equals the release commit; M1Max gains the ADR 0075/0077/0078 fixes and M4Pro
  loses its unpublished local-build provenance.
- The OTA page offers macOS 1.1.8 and the paired iOS OTA 98 to registered
  devices; other channels are unchanged.
- In-app update feeds remain unavailable until a feed key is supplied.
- Superseded releases remain on the server until the owner authorizes a prune.

## Verification

Recorded separately below (implementation and device acceptance are distinct):
source ancestry and fingerprint gates, build and Swift compilation, Developer
ID signing and strict signature verification, presence signing, notarization
`Accepted`, stapling and Gatekeeper, package hashes, iOS archive signing and
profile, published pages/manifest/hashes/cache headers read back over HTTPS,
per-Mac version/build/commit/daemon hash/identity/backup, relay/Vnet/
Accessibility, six RPC directions and 24 ping directions, and the open
acceptance limits. No real conversation is used as a release test.

### Source, build and signing — 2026-11-02

- The only built source was the merge commit of PR 81,
  `8c79329d4d0464bcfef05bfea7e8c95407d9b76d`; the release worktree was a clean
  detached checkout of it. `cargo build --release` for the daemon, CLI, relay
  and browser host, the Apple FFI archive and the Xcode Release app all
  succeeded.
- The built daemon carried exactly one `MUSTER-BUILD-COMMIT:8c79329d…` stamp;
  `verify-release.sh` reported the release ancestry and shipped fingerprints
  verified, and presence signing verified for `89LGY6BD53.dev.linsheng.muster`.
- The packed bundle passed strict `codesign --verify --deep`, `spctl` reported
  `accepted, source=Notarized Developer ID`, and `xcrun stapler validate`
  passed after notarization `9b8a05a6-86c2-465d-8aff-b5777b83193f` returned
  `Accepted`.
- Desktop portable ZIP SHA-256:
  `252bbede03f9676deb6dd583d713a1d548a738427bc8d8638f051f2b34aff30b`.
  Packaged daemon SHA-256:
  `a0ca38b5912262e9529367aea5f8ea6b5458bb32e1eca0a9ee1bd4b029ca883b`.
  The bundle's `sq.version` reports 1.1.8.
- The paired iOS archive built as 1.1.8 (98), team `89LGY6BD53`,

### Publication and public read-back — 2026-11-02

- The publisher accepted all 11 staged files and verified their hashes on the
  server (`{"published_files":11,"mac_version":"1.1.8","ios_version":"1.1.8","build":"98","hashes_verified":true}`).
- Read back over HTTPS: the root, `ios/` and `desktop/` pages equal the
  generated page; the Mac portable and the IPA match their SHA-256 values; the
  manifest names build 98 and the hash-named IPA; the previous 1.1.6 manifest
  URL redirects to the current manifest; the pages, manifest, packages and
  `SHA256SUMS` carry
  `no-store, no-cache, must-revalidate, max-age=0`.
- No signed Velopack update feed was published, for the reason in Decision.
  Superseded releases were **not** pruned; the server-side prune still needs
  explicit owner authorization.

### Installation and runtime — three Macs, 2026-11-02

- One identical notarized portable was installed on the three Macs, one at a
  time, over routes that do not depend on the device's own daemon: the local
  Mac, a physical Thunderbolt/LAN route, and a temporary reverse tunnel that
  was removed after acceptance. The installer kept a previous-bundle copy on
  each Mac.
- All three report desktop **1.1.8 (98)**, commit prefix `8c79329d`, the
  packaged daemon SHA-256 above, and unchanged device identity, fingerprint and
  Secure Enclave backend. Accessibility is granted, the relay is registered and
  Vnet is up on each; strict signature, notarized-DM status and stapling pass
  on the installed bundle.
- Six cross-device RPC directions succeeded and 24 of 24 virtual-IP ping
  packets were received with no loss. The managed task scheduler on one Mac was
  suspended and restored around the replacement; its own installer window saw
  the scheduler still recovering, and an immediate direct re-check reported it
  `running`. That is delayed success, not a failed install, and nothing was
  reinstalled.
- Not verified: no real conversation was used as a send test, so ADR 0080's
  device acceptance (a send to a session that is not the open one) remains
  open; physical iPhone installation, GitHub Release, TestFlight, App Store
  submission and the server prune were not performed.

## Verification status

Published and installed. The macOS and iOS artifacts are public on the unified
OTA page; the three Macs are on the same notarized build with their identities
preserved. Provider-level send acceptance and physical iPhone installation
remain owner-side steps.
