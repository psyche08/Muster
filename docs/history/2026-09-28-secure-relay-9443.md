## Implemented

`muster.linsheng.dev:9443` is one relay authority with two secure carriers:
TCP/TLS 1.3 and UDP/QUIC. Both load the same certificate chain/key and use
`muster-relay/1` ALPN. Production clients validate the public CA chain and
hostname; device authentication and inner peer encryption remain independent.
The deployment scripts use the existing Let's Encrypt certificate lineage.

Shared Rust resolves the authority through DoH and owns parallel connection
attempts, the three-second connection deadline, padded nonce probes, RTT-based
selection, switch hysteresis, activation, and reconnect backoff. Carrier changes
do not replay application operations. The inner QUIC connection handles packet
recovery. An outer carrier's reflected address is not an inner NAT candidate.

## Initial handoff: deployment pending

No new app signing, notarization, device installation, production cutover, or
public dual-carrier end-to-end acceptance was performed in this turn. The old
relay remained active after the isolated build. New clients and the new server
must be rolled out together because the production wire transport changes.

The SSH account cannot run administrative commands noninteractively. Existing
`musterd.service` owns TCP `127.0.0.1:9443`; it is a separate legacy service and
must not be stopped as part of this rollout. The new relay can bind the server's
ingress address `192.0.2.42:9443` for both protocols. Confirm that the existing
public TCP/UDP port mapping targets this address before cutover.

Once the matching signed clients are ready, the administrator can run on the
server (this restarts `muster-relay.service`):

```sh
sudo env CERT_DIR=/etc/letsencrypt/live/linsheng.dev \
  RELAY_LISTEN=192.0.2.42:9443 \
  /home/developer/muster-secure-9443-20260928/src/muster/deploy/relay/install.sh \
  muster.linsheng.dev
```

The installer validates the certificate/key, copies them with restricted access,
and installs the TLS/QUIC service. Configure the documented certificate-renewal
hook as part of cutover. From an external network, run the matching
`relay_probe muster.linsheng.dev:9443 --require-both`, followed by real-device
RPC, network-change, and foreground/background recovery checks. A successful
probe alone does not establish real-device acceptance.
