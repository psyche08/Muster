## Status Definitions

- **Implemented**: the actual production path is wired; merely defining an interface, declaring capability, or displaying a button does not count.
- **Tested**: state the actual test boundary. Software keys, local sockets, simulated storage, and production-adapter contract tests are not physical hardware validation.
- **Built**: identify the build target; an unsigned HAP or local release build does not mean signed, notarized, or installed.
- **Deployed**: confirm that mutually matching versions are installed and retain installation evidence.
- **Accepted**: validate the complete user flow on actual Mac, HarmonyOS devices, Relay, Secure Enclave/HUKS, and Providers.
- Unchecked items below still require completion or evidence. Checked source items do not mean their corresponding physical-device flows have been accepted.

## 6. Security and Completion Conditions

- Shared Rust must own platform-independent business logic, authorization, validation, network orchestration, durable transitions; Apps only handle UI/input/lifecycle/OS capabilities.
- Directory visibility, HTTP 200, certificate completion, copied artifacts, and installer exit codes cannot replace full pairing/access evidence.
- Mock/local-socket/software-key tests must not be described as real Relay/Secure Enclave/HUKS/Provider acceptance.
- Do not conceal recovery defects by clearing pairing, unfinished issuance, journals, or caches; cleanup requires separately confirming exact scope/security grounds.
- Never run `security unlock-keychain` or request/handle Keychain passwords; blocked signing requires the user to unlock interactively in Keychain Access.
- Single-device local revocation, whole-listener restart, consumer receipt of revocation, and global propagation are separate gates, not one completion claim.
- Until all implementation, matching deployment, and actual flows have corresponding evidence, the goal remains incomplete; do not narrow this checklist to the latest easiest subtask.
